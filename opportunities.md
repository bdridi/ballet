# Ballet — opportunités

Ce qui reste à faire, à vérifier ou à trancher dans Ballet. La méthode est dans `PRD.md`, ce qui est livré dans `release.md`.

- 🆕 à traiter · ✅ traité (avec la version qui l'a livré, reportée dans `release.md`)
- Un sujet garde son numéro pour toujours ; un sujet traité reste ici, coché. Pas de doublon : un nouveau besoin proche d'un sujet existant l'enrichit.
- Dans chaque section, du plus pressé au plus lointain.

## La vision

- **La file, c'est GitHub.** Une issue a un type (`task`, `bug`, `feature`, `slice`) et un statut ; une `task`, un `bug` ou une `feature` au statut prêt attend sa Rehearsal. Les slices naissent de la planification d'une feature et se jouent à sa suite.
- **Un observateur déterministe** (un script, pas un agent : le Monitor) surveille la file et signale l'élément prêt ; il ne lance rien. C'est Maestro qui lance une session de Conductor neuve, seul pour ce que le projet confie à l'auto, sinon sur le oui du Director. L'état vit dans les scripts et sur GitHub : rien à garder en mémoire d'une session à l'autre.
- **Chaque boucle tourne en `assisted` par défaut**, ou en `autopilot` quand on la lance ainsi.
- **Le Workshop sort une feature prête, jamais un plan.** Le Choreographer y donne son avis technique tôt, parce qu'il peut changer le choix produit. En assisted, le Director, le Dramaturg et le Choreographer ; en autopilot, le Dramaturg et le Choreographer seuls, et la feature sort proposée, prête une fois que le Director l'accepte ; le full autopilot (prête d'emblée) reste une option.
- **La Rehearsal planifie sur le vrai `main`** : le Choreographer commence par le plan, juste avant le Dancer, pour qu'il ne se périme pas. En assisted, elle escalade vers le Director ; en autopilot, c'est le mode nuit.
- **En autopilot, chacun décide dans son périmètre** : le Dramaturg tranche le métier ; le Choreographer l'architecture, et demande le métier au Dramaturg ; le Dancer suit l'architecture, et demande au Choreographer. Ce qui est décidé sans le Director est marqué et réuni dans un rapport du matin ; il ne reçoit en direct que ce qui sort de tous les périmètres.
- **Un budget** borne ce que l'autopilot dépense.
- **Maestro**, le point d'entrée du Director pour plusieurs projets, et le seul à lancer les Conductors (OPP-02).

  - **Le canal, c'est Orca** : la boîte de Maestro, une Run (`run:<id>`) créée `--from` un terminal Orca à lui seul. Messages de type `status` (Orca réserve `escalation` aux workers dispatchés), priorité `high` pour ce qui attend le Director, sujet `<projet>#<élément> · <événement>`. Maestro attend avec `orchestration check --wait`, en arrière-plan : il dort sans coût et se réveille à chaque message. Orca garde le lu et le non-lu, et l'historique (`orchestration inbox --full`) ; la Run et ses messages survivent à un redémarrage d'`orca serve`.
  - **Le Conductor pousse lui-même** : `ballet_rehearsal.py` et `ballet_workshop.py` envoient un `status` à la boîte à chaque `NEXT: escalate` (question comprise) et `NEXT: done`. Réveil immédiat ; le Conductor ne fait toujours que relayer.
  - **Deux rôles distincts** : le **Monitor** observe et signale, sans jamais lancer ni parler au Director ; **Maestro** décide et déclenche tout (lancements, réponses), sans jamais surveiller (il attend la boîte). Maestro et le Monitor sont au vocabulaire (PRD §3).
  - **Le Monitor `ballet_monitor.py`** (sans LLM, dans son propre terminal Orca ; c'est l'observateur d'OPP-01, étendu à plusieurs projets) écrit dans la même boîte ce que lui seul voit : un élément passé `ready` sur GitHub (`ballet_program.py`, transitions déjà vues gardées : idempotent) ; un Conductor mort ou figé qui n'a rien envoyé. Il ne lance aucun Conductor. Il marque terminée la ligne du registre d'un Conductor fini (`done`) ou dont le terminal est mort. Ne coûte aucun token.
  - **Deux modes d'installation**, choisis au setup (OPP-74) : **présentiel** (le poste du Director, Orca desktop ouvert : le Monitor dans un terminal Orca, Maestro dans une session Claude du Director, avec son terminal-boîte ; s'il meurt, le Director le relance, pas de gardien) et **headless** (un VPS, `orca serve` sous systemd, Maestro en Remote Control, et le gardien).
  - **Le gardien `ballet_keeper.py`** (nom à trouver ; **en headless seulement** ; sans LLM, hors d'Orca) garde vivants les trois terminaux Orca de l'ensemble : la boîte, le Monitor et Maestro. Une boucle : chacun existe-t-il, répond-il ? Sinon il le recrée (`orca terminal create --command …`, qui marche sans handle), note le nouveau handle dans `~/.ballet/maestro.toml` et le dit dans la boîte (« Maestro relancé »). Lui-même tourne sous systemd (launchd sur le Mac), après `orca serve`, qui le relance s'il meurt. Il ne lance aucun Conductor. La boîte recréée : la nouvelle Run est notée, l'ancienne relue une dernière fois par Maestro.
  - **Maestro déclenche tout, par `ballet_launch.py`** (un script, un objectif, appelé par lui seul). À un élément passé `ready`, il applique la règle du projet : un type confié à l'auto (`auto_launch` de son projet dans `maestro.toml`), sans drapeau de pause, il le lance tout de suite et le dit au Director après coup ; sinon il demande et lance sur son oui. Garde-fous, vérifiés par `ballet_launch.py` : projets autorisés, plafond de Conductors simultanés et par jour, budget (OPP-53). Le script crée le terminal Orca, lance `claude --remote-control '<projet>#<élément>' … /ballet:rehearsal #N` (ou `/ballet:workshop --autopilot`) et écrit la ligne du registre. Le Monitor et Maestro ne se parlent jamais : ils partagent `~/.ballet/` (plus tard la base) et la boîte, où le Monitor écrit et Maestro lit. Le prix : l'autonomie dépend d'un Maestro vivant ; mort la nuit, un élément prêt attend dans la boîte jusqu'à sa relance, que le gardien assure.
  - **Le skill `/ballet:maestro`** (la conversation) : `status` (toutes les sessions, tous les projets), `launch <projet> <élément>` (Rehearsal ou Workshop, par `ballet_launch.py`), `tell <élément> <réponse>` (`orca terminal send` : le Conductor écrit le message Ballet et lance `receive`, il reste le seul à jouer sa session), `stop <élément>`. La session est jetable : tuée ou nettoyée (`/clear`), les Conductors et le Monitor continuent, les messages attendent ; au redémarrage elle relit le non-lu et les derniers messages de l'historique (un message lu juste avant la mort de la session n'est plus non lu), réarme son attente de la boîte et commence par « pendant ton absence ».
  - **Les Conductors en Remote Control** : lancés par `terminal create --command "claude --remote-control '<projet>#<élément>' …"` (vérifié au spike), le Director peut aussi leur parler en direct ; Maestro relit leur session avant de porter une réponse, pour ne pas répondre deux fois.
  - **La V1 tient dans des fichiers, sous `~/.ballet/`** : `maestro.toml` (les projets, leur alias et leur chemin ; les types en `auto_launch` ; les plafonds ; le handle du terminal de la boîte et l'id de sa Run) et `conductors.json`, le registre : un Conductor par ligne, avec son élément, son projet, son handle Orca, son URL Remote Control et son début. Écrit par `ballet_launch.py` (une ligne par lancement, écriture atomique : fichier temporaire puis renommage) et par le Monitor (la ligne marquée terminée), jamais sur la même ligne au même moment. L'état d'une Rehearsal reste dans son projet (`.ballet/run/`) et sur GitHub : le registre ne dit que qui tourne, où, et par quel terminal.
  - **La boîte survit à la session de Maestro** : elle ne vit pas dans sa session Claude mais dans Orca. Le terminal de la boîte est un shell vide qui ne fait rien d'autre, et la Run et ses messages sont gardés par Orca (au spike, tous deux ont survécu à un redémarrage d'`orca serve`). Une nouvelle session reprend le même handle et la même Run, lus dans `maestro.toml`. **À vérifier** : si le terminal de la boîte lui-même est fermé, un nouveau terminal peut-il reprendre la Run (`orchestration run-use`, ou `inbox --terminal run:<id>`) ? Sinon, le Monitor recrée boîte et Run, et Maestro relit l'ancienne une dernière fois.
  - **Redémarrer Maestro ne perd rien** : tué ou relancé (contexte trop lourd, `/clear`), les Conductors continuent, ceux qui attendent le Director restent en pause sans délai, le Monitor surveille et signale, les messages s'accumulent (un élément prêt, même en auto, attend Maestro) ; mort, Maestro est relancé par le gardien. Au redémarrage, `/ballet:maestro` relit le registre et l'état des sessions, le non-lu de la boîte et les derniers messages de l'historique (un message lu juste avant la mort de la session n'est plus non lu), dit « pendant ton absence : … », puis réarme son attente. Le seul moment à éviter : pendant qu'il porte une réponse à un Conductor. En option, `/ballet:maestro restart --when-idle` : Maestro pose le drapeau `~/.ballet/auto_launch_paused` (il ne lance plus rien d'automatique, y compris juste après son redémarrage), attend qu'aucun Conductor ne travaille (une pause sur escalade ne compte pas), redémarre, puis retire le drapeau.
  - **Plus tard, un état au niveau de l'utilisateur, en SQLite** (`~/.ballet/ballet.db`, `sqlite3` de la bibliothèque standard), qui n'est pas le canal : les projets (alias, chemin), le registre des Conductors (une table `conductors`, qui remplace `conductors.json` ; la base tient les écritures concurrentes en WAL), et l'historique de tous les projets, chacun rangé par projet (colonne `project`), que la Scène lit en un seul endroit (OPP-73). À faire : le schéma, la migration des `journal.jsonl`, l'écriture concurrente (WAL), les scripts qui écrivent ou lisent le journal. La V1 de Maestro s'en passe (des fichiers suffisent).
  - **Fini quand** le Director, depuis la seule session de Maestro, voit l'état de tous ses projets, lance une Rehearsal ou un Workshop dans le bon dossier, reçoit une escalade sans lire de terminal et y répond ; qu'un élément passé `ready` part en Rehearsal (seul ou sur son oui, selon le projet) ; et qu'une session de Maestro relancée reprend sans rien perdre.

- 🆕 **OPP-06 · Workshop autopilot** (chapeau, découpé en OPP-68 ✅ 0.31.0, OPP-70 ✅ 0.32.0 et OPP-69 : chacune se livre seule) : le Dramaturg et le Choreographer, sans le Director, dans une session de Conductor comme la Rehearsal, visible sur la Scène. Il cadre une demande, un bug ou un retour, ou choisit lui-même dans le backlog. Sortie : des features proposées, que le Director accepte avant qu'elles entrent dans la file ; en option, le full autopilot les rend prêtes d'emblée. **Décisions prises (à contester si besoin) :**
  - **Un seul mode, `autopilot`** ; le portillon du Director est un réglage à part, `Queue approval` (`required` par défaut : la sortie est `proposed` ; `skipped` : elle est `ready`), sur le modèle de `Plan approval`. Écartés : un mode `autopilot-proposed` (le PRD veut deux modes par boucle, et en Rehearsal `autopilot` veut dire « le Director est hors de la boucle »), `autopilot` / `full autopilot` comme deux sous-modes, `autopilot → proposed` / `→ ready`. Le mot « acceptance » est évité (collision avec les critères d'acceptation du BDD). **`full autopilot`** nomme la combinaison Workshop `autopilot` avec `Queue approval: skipped`, puis Rehearsal `autopilot` : de l'idée à `main` sans humain.
  - **Le réglage est dans le profil, par type de travail** (l'issue n'existe pas encore) : `[workshop] queue_approval_skipped = []` (types `Feature`, `Bug`, `Task` ; vide : tout passe par le Director). Le PRD (§6, §13) réserve le `ready` d'emblée aux projets et types choisis. Commencer par `Bug` ou `Task` seulement : un bug a la spec pour arbitre, alors qu'une feature fait deviner du métier au Dramaturg, et ce qu'il devine part en Rehearsal autopilot sans relecture.
  - **La commande** : `/ballet:workshop` est assisted par défaut (une session live avec le Dramaturg, l'avis du Choreographer au besoin : OPP-05) ; `/ballet:workshop --autopilot <élément>` est autonome. Pas d'issue où lire le mode d'un Workshop : c'est le flag `--autopilot`, comme le PRD §11 l'écrivait (OPP-08, qui veut des commandes sans flag, lit le mode d'une Rehearsal sur son issue, ce qui n'est pas possible ici).
  - **Passer `proposed` à `ready`** : le Director change le champ `Ballet status` dans l'interface GitHub, c'est suffisant au départ ; aucune opération de script nécessaire.
  - **Le plus risqué** (PRD §13) est le Workshop qui choisit seul dans le backlog ; le PRD §14 le met hors V1 sans propositions. D'où l'ordre : un élément donné d'abord (OPP-68), le choix dans le backlog ensuite, toujours en `proposed`.
  - **Dépendances** : la marque `ballet:decided-alone` d'OPP-04 (au minimum la marque sur l'issue), le rapport du matin d'OPP-52, l'observateur d'OPP-01 pour un déclencheur à heure fixe (hors d'OPP-06, voir la question ouverte du PRD §15). Principe de coût (mémoire « cost over ceremony ») : peu de tours, trois slices au plus par opportunité.
